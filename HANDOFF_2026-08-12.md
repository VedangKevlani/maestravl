## Non-negotiables (unchanged, repeat to any new session)

- **Zero new paid services** beyond what's already free-tier-with-no-card,
  or explicitly flagged as paid-but-cheap and opt-in (MiniMax web search,
  ~$0.01/call).
- **Never fake success.** Nothing claims a provider confirmed, contacted,
  or resolved something it didn't actually verify. An `AgentRun` only
  reaches `CONFIRMED` when a human explicitly confirmed it.
- **Deterministic logic first, AI layered on later.** The one deliberate
  exception is `lib/agents/replyInterpretation.ts` — reading what a reply
  *means* is genuine language understanding, not something a regex can do.

**This session's work, all committed and pushed to `origin/master`:**

1. **Trust & verification surfaces.** `GET /api/agent-runs/[id]/communications`
   + a "View messages" panel in `TripRecoveryStatus.tsx` — the first
   client-facing read of real `Communication` content (the actual email
   sent, the actual reply received) anywhere in the app, replacing
   paraphrased `AgentAction.description` text as the only visible "proof."
   A new `/system-health` page (linked in the header) reports each
   integration's status from real database evidence (e.g. inbound-reply
   detection only shows "confirmed" once a real `INBOUND` `Communication`
   row exists), not just whether an env var is set.
2. **Live status widget redesign.** The banner now shows the real latest
   `AgentAction` description, fading in as it changes, instead of a
   generic `STATUS_COPY` phrase.
3. **Reply interpretation.** `lib/agents/replyInterpretation.ts` — a
   scoped Gemini call (reusing the voice assistant's free-tier model)
   classifies a provider's reply as ACCEPTED/DECLINED/COUNTER_OFFER/
   UNCLEAR. A confident ACCEPTED read moves the run to `RESCHEDULING`
   (finally giving that enum value real meaning) but never auto-confirms —
   the passenger sees the interpreted summary next to the real reply text
   and must explicitly hit "Confirm — update itinerary"
   (`app/api/agent-runs/[id]/confirm-reschedule`), which is also the first
   real use of `AgentActionType.UPDATE_ITINERARY` anywhere in the codebase.
4. **Real train/bus monitoring**, backed by
   [Transitland](https://transit.land) (`lib/monitoring/adapters/transitland/`)
   — a free-tier (10,000 REST queries/month) GTFS/GTFS-realtime aggregator
   found independently (none of the team's sponsor resources — Boardy,
   Nebius, OllyGarden, Giotto.ai — turned out to be transit-data sources).
   `trainAdapter.ts`/`busAdapter.ts` are real now, not stubs. Real
   constraint: only matches once a segment has its operator name + train/
   bus number manually filled in (auto-extraction never sets these for
   non-flight segments) — degrades to an honest, actionable message
   otherwise. **Unverified against live data — no API key was available
   while building it** (see "What's left," below).
5. **"Get an Uber there" deep link** (`lib/uber.ts`). Investigated real
   Uber API booking first (Riders API, Guest Rides/Uber for Business) —
   both are book-and-track only, can't check status of a ride booked
   elsewhere, and real in-app booking would mean building payment
   infrastructure from scratch plus a real per-ride fare cost. Went with a
   zero-liability deep link instead: opens Uber's own app/website with
   pickup/dropoff prefilled from whatever location text is available,
   shown on a `SegmentCard` when that segment is delayed/cancelled and a
   next segment exists. **Also unverified against a real client_id.**
6. **A real, previously-undiscovered OCR bug, fixed.** Any scanned/
   image-only PDF upload was silently crashing instead of falling back to
   OCR — `extractText.ts` reused the same buffer for two sequential pdf.js
   loads, and pdf.js detaches the underlying `ArrayBuffer` after the first
   load. Never caught before because the existing e2e test only uploads a
   plain PNG, never a scanned PDF. Fixed in `lib/extraction/pdfText.ts` by
   copying bytes before handing them to pdf.js.
7. **OCR quality improvements, measured not assumed.** Bumped PDF render
   DPI from 144→300 (Tesseract's documented sweet spot) and set
   `preserve_interword_spaces: '1'` (helps the regex-based field parser
   read label/value spacing correctly). Verified before/after on the same
   test document: **OCR confidence 86→90**, with concrete errors fixed
   ("Amival"→"Arrival", "American Afines"→"American Airlines", garbled
   closing sentence fully cleaned up). Image preprocessing (grayscale/
   contrast/deskew) is a documented but *not yet built* next lever — likely
   more useful for genuinely degraded real-world scans than the clean
   synthetic test fixture showed room for.
8. **Two realistic test itinerary PDFs**, generated via Playwright
   (`e2e/fixtures/make-test-itinerary-pdf.mjs`, gitignored outputs, also
   copied to the Desktop): a 2-flight connection (Kingston→Miami→JFK) plus
   a hotel stay — `test-itinerary.pdf` (real text layer, exercises the
   native-pdf path) and `test-itinerary-scanned.pdf` (image-only, forces
   the OCR path).

## What's genuinely left

1. **Verify the Transitland adapter against live data.** No
   `TRANSITLAND_API_KEY` was available while building it. Specifically
   unconfirmed: whether the free tier truly needs no card, the exact JSON
   shape of a GTFS-RT Alert in Transitland's REST responses
   (`lib/monitoring/adapters/transitland/matching.ts`'s `classifyAlerts`
   was written defensively from the GTFS-RT spec + their docs, may need
   adjustment), and whether `route_type` or `route_types` is the correct
   query param (`transitland/client.ts` picked `route_type`, flagged
   inline as unconfirmed). Watch `/system-health`'s train/bus row — it
   only turns "confirmed" on a real operator+route match.
2. **Verify the Uber deep link against a real client_id.** The URL format
   (`m.uber.com/looking?client_id=...`) came from Uber's own docs page, but
   a secondary source cited a different path (`m.uber.com/ul/`) — neither
   confirmed against a live click-through.
3. **Rental car / taxi / ferry / cruise monitoring genuinely has no free
   path.** Researched this session (Avis/Booking.com/OpenNDC are all
   partner-agreement-gated), documented in `docs/INTEGRATION.md` so it
   isn't re-researched from scratch later. Real booking via Uber's Guest
   Rides API remains a deliberately deferred, much larger feature (no
   payment infra anywhere in this app, real fare cost per ride, Uber for
   Business approval needed, an unresolved "who's billed" question).
4. **Pick between reschedule Option A/B based on reply content.**
   `classifyReply` reads intent, not which specific proposed time was
   accepted — `confirm-reschedule` always applies the primary
   `RescheduleRequest.requestedTime` regardless.
5. **OCR image preprocessing** (grayscale/contrast/deskew) — a real lever,
   not yet built, likely more valuable for real degraded scans than the
   clean test fixture used this session.
6. **Run the Phase 9 end-to-end demo scenario as a real test** — the
   Jamaica scenario in `AGENTS.md` has never been run end-to-end as one
   narrative. Use it to surface Phase 10 hardening gaps (duplicate
   disruptions, race conditions, partial failures) rather than guessing.
7. **Live-verify the inbound-reply pipeline in actual production** —
   `/system-health` gives a standing signal for this now, but nobody has
   actually triggered a real provider reply yet to confirm it flips.
8. Boarding pass QR (BCBP) decoding, wallet export, calendar (.ics) export
   — still just "future ready" in `docs/INTEGRATION.md`, never built.
